# Crawlers — Gaps and decisions

**Architecture:** [00-architecture.md](00-architecture.md) · **Rollout:** [01-rollout.md](01-rollout.md)

## Settled

| # | Decision |
| --- | --- |
| D1 | **Queue consumer.** The crawl layer consumes the existing `discovery_task` queue. There is no standalone `apps/crawler` package, no `sources.yaml`, and no direct `POST /suggestions` from workers. |
| D2 | **New task kinds in the same table.** `harvest_payload`, `extract_page` and `capture_screenshot` extend the existing enum, and `render_page` joins them in chapter 14. Separate tables or queues were rejected: they would rebuild leases, reclaim, dedup, metrics and the admin Tasks view. |
| D3 | **Kind-filtered claim, safe default.** Workers send `kinds`; when omitted the API serves only the two legacy kinds so the scheduled drain cannot lease and fail an unknown kind. |
| D4 | **Workers orchestrate, API persists.** Follow-up tasks are enqueued by the worker through an idempotent machine route because only the worker knows which extractors exist. Workers never hold `DATABASE_URL`. |
| D5 | **A procedure is not a document.** Catalogue services stay staging context. Document nodes come only from what a procedure requires or provides (forms, evidence, documents to bring). Service-level `new_document` claims from FIM enrichment stay staged and are excluded from the document-first path. |
| D6 | **Documents first, edges later.** This suite harvests, deduplicates, reviews and emits document candidates. Mentions keep the `requires` relation so the later dependency-graph suite needs no re-crawl. |
| D7 | **Candidate key equals the promotion slug rule.** `key = slugify(pick_title(title_i18n))` from [slugs.py](../../apps/api/app/features/suggestions/slugs.py), so two candidates never collide at promotion that did not already collide as candidates. |
| D8 | **`official_url` becomes optional on `new_document`.** Conflicts are detected on slug or normalized URL per jurisdiction ([handlers.py](../../apps/api/app/features/suggestions/handlers.py)), so a shared procedure URL cannot serve as a fallback. Many documents ("Personalausweis") have no URL of their own. The change is additive; `Document.official_url` is already nullable; provenance travels in `suggestion.source_url`. |
| D9 | **Both artifact kinds live in the object store; Postgres holds metadata only.** Rejected alternative: gzip'd `bytea` snapshots in Postgres (about 12–20 MB for today's 1,423 pages). The free database is capped at 500 MB and goes read-only on overflow, whereas a full bucket only blocks uploads. |
| D10 | **Cloudflare R2, behind an `ObjectStore` port.** One S3 adapter pointed at `https://<account_id>.r2.cloudflarestorage.com` (region `auto`); another S3 service is a configuration swap. R2 replaces the earlier Supabase Storage choice (revised 2026-10-26): 10 GB against 1 GB, free egress, and one provider fewer, because the Cloudflare account already hosts the frontend and Browser Run. The earlier evidence-storage plan had also chosen R2; that suite is amended in chapter 21. Supabase stays Postgres and auth only. |
| D11 | **Uploads are proxied through the API.** Storage credentials live only in Render. Reads use five-minute presigned GET URLs minted per request. |
| D12 | **Snapshots are working input, screenshots are evidence.** Snapshots: the rendered DOM as `text/html`, 4 MB cap (a rendered DOM is larger than the raw response), latest two per service, deduplicated by sha256. Screenshots: PNG or JPEG, 8 MB cap, durable. HTML is never rendered inline in the admin. |
| D13 | **Screenshots only for pages that yielded documents.** A screenshot task is enqueued only after an extraction produced at least one mention, and login walls are skipped. Evidence of a login page has no value. The Cloudflare snapshot endpoint could return an image for every page at no extra call, but 1,423 images would approach the 1 GB storage cap and spend browser time on pages that yield nothing. |
| D14 | **Pages are rendered by Cloudflare Browser Run quick actions, not by a browser we run.** The worker calls `/content` (rendered DOM) and `/snapshot` (DOM plus image) through a `BrowserClient` port with a Cloudflare adapter. No Playwright, no `[capture]` extra, no Chromium install, no browser CI job, no browser in any image. This replaces the earlier decision to run Playwright in a dedicated workflow; the rendered DOM also makes JavaScript shells (such as `fimportal.de/detail/...`) extractable. The Cloudflare account already hosts the frontend, so the free plan costs nothing. |
| D15 | **Retries only for transient failures.** 5xx, timeout and connection reset re-pend with backoff up to a cap; 4xx stays failed. |
| D16 | **Manual emit remains deliberate.** Scheduled jobs never emit. Candidate emit is idempotent per candidate and records the suggestion on the candidate. |
| D17 | **GitHub Actions is the test bench.** Local development is limited, so chapters verify with PR checks and `gh workflow run`; the non-production stack may be used freely. |
| D18 | **Navigation links are `react-icons` buttons in one `HStack` row,** driven by the config array. Never a new row, never a text link. |
| D19 | **The plain fetch stays the gate; Cloudflare renders.** `fetch_url` keeps its robots, pacing, redirect and status handling and logs the outcome. Only a 200 `text/html` result whose final URL is not a login URL enqueues a `render_page` task. Browser time is never spent on redirects, errors or login pages, and the merged chapter 2 work stays useful. Rejected: replacing the plain fetch with a render (loses the status and redirect log, spends browser time on everything). |
| D20 | **The free-plan limits are a design input.** 10 browser minutes a day, one quick-action request every 10 seconds, 3 concurrent browsers, 60 s timeout. The worker serialises calls at least 11 s apart (counted from the end of the previous call, D26), sums `X-Browser-Ms-Used` against a per-run budget (default 480 s), and stops on `429`. The rate limit normally binds before the browser minutes (about 4 pages a minute, so 55 to 65 pages per 15-minute run, measured in chapter 15). Browser kinds live in their own kind-filtered workflow and are never in the default kinds, so the HTTP drain never waits on the throttle. |
| D21 | **Limits release tasks; only pages fail them.** A quota `429`, an exhausted browser budget, or unavailable storage says nothing about the page, and attempts are consumed at claim time (cap 3). The worker therefore calls a new release route (`POST /machine/tasks/{id}/release`, chapter 14) for the in-flight task and every unstarted task of the batch, which re-pends them and gives the attempt back, then ends the run successfully. Browser drains claim small batches (5). |
| D22 | **The Cloudflare token is narrow and stays out of the API.** A custom token with only "Browser Run - Edit", stored as GitHub Actions secrets and in the operator's local environment. Quick-action requests are signed by Cloudflare (Web Bot Auth) and cannot hide that they are automated; the worker still checks robots.txt itself and sends its identifying User-Agent as the quick action's `userAgent`. |
| D23 | **A server-side budget ledger guards every free allocation.** A `discovery_budget_ledger` table in the API records usage per period and resource (R2 operations, browser seconds, neurons, Actions minutes); caps live in API settings and sit below the allowances with a margin. Workers read the remaining budget before spending and report spend after, so GitHub runs, local runs and concurrent runs share one count. A per-run budget alone cannot do this. Chapter 23 builds it; chapters 15, 19 and the extraction suite consume it. |
| D24 | **Resources that bill are capped by us.** R2 does not stop at 10 GB, it bills, and Workers AI bills on a paid Workers plan. `OBJECT_STORE_MAX_BYTES` (default 8 GiB) is enforced on upload (507, nothing written), R2 operations are counted and capped monthly, the Workers AI daily cap is reserved before each call, and the operator keeps the account on Workers Free and sets Cloudflare billing notifications (chapter 22). Supabase gets a 400 MB soft limit on machine writes because the project goes read-only at 500 MB. The GitHub Actions share of this repository is capped at 1,000 minutes a month (GitHub's free 2,000 are shared across repositories), of which a CI reserve is not spendable by the drain workflows. |
| D25 | **The steckbrief key is the LeiKa key; FIM enrichment fires for GovData and PVOG (chapter 12, probed 2026-10-26).** Ten sampled keys (five GovData `leika_key`, five PVOG `leikakeys[0]`) all returned 200 with `leistungsschluessel` through `fim probe`, so the decision gate passed (10 of 10) and the LeiKa stammtext route stays unused. Resolution order in fanout and `fim_id_from_catalogue`: `fim_id`, `leistungsschluessel`, `leika_key`, `leikakeys[0]`; the first value matching `[0-9]{14}` wins, so a malformed `fim_id` falls through to `leika_key`. **Real steckbrief top-level keys:** `redaktion_id`, `leistung_id`, `title`, `title_en`, `leistungsbezeichnung`, `leistungsbezeichnung_en`, `leistungsbezeichnung_2`, `leistungsbezeichnung_2_en`, `rechtsgrundlagen`, `rechtsgrundlagen_en`, `freigabe_status`, `erstellt_datum_zeit`, `geaendert_datum_zeit`, `leistungsadressat`, `leistungsschluessel`, `typisierung`, `leistungstyp`, `sdg_informationsbereiche`, `klassifizierung`, `leistung_stammtexte`, `prozessklasse`, `ozg`, `replacements`. **The steckbrief carries no document, form or evidence field**, so chapter 12's Loop C (a `fim-steckbrief` mention mapper) does not apply. `leistung_stammtexte` lists `{redaktion_id, id, title, leistungsschluessel}` references to the text modules, which is where Unterlagen or forms could live; that is a separate fetch (`/leistung-stammtexte/{redaktion_id}/{id}`) and an open seam. **Label fix (follow-up `fix/crawlers-fim-title`, 2026-10-27).** The enrich helpers had read `titel` and `kurztext`, but the real response has `title` and no `kurztext`, so the entity label stayed empty. The label now comes from the first non-blank of `title`, `titel` (legacy early-fixture shape, kept so older payloads still work), `leistungsbezeichnung`; with none of them the entity is created without a label. The `metadata` claim (`kurztext`) is unchanged in shape and is written only when a real `kurztext` exists; the real steckbrief has none, so enriched entities get the label and the service-level `new_document` claim (staged, excluded by D5) but no `metadata` claim, and no other field is substituted. The `new_document` title still comes from the catalogue row. The LeiKa stammtext helper still reads `titel` and `kurztext` (shape not probed). |
| D26 | **The first live Browser Run probe settled the response shape and moved the design (chapter 15, 2026-10-27).** `/content` answers at `browser-run/content` with a JSON envelope `{success, result, meta{status, finalUrl, title, headers, redirectChain}}`, and Cloudflare answers `200` even when the target answered `404`, so the target's HTTP status and final URL **are** available (reversing the earlier assumption that the design needs neither). The handler therefore refuses to store a page whose `meta.status` is 400 or higher (5xx retryable, 4xx permanent) and records `meta.finalUrl` as the artifact's `final_url`. An unresolvable host is `422` code 5006. The free plan's rate limit (`429` code 2001, `Retry-After: 10`) fired for a call that started 11 s after the start of a 6.3 s call, so the throttle counts from the **end** of the previous call and a rate-limit `429` is retried once before the run stops. `X-Browser-Ms-Used` could not be read as an integer on any `200` (present on the `422` and `429`), so the client parses fractions and falls back to the measured duration. `userAgent` is honoured; `rejectResourceTypes` did not save time and is not sent. Rendered DOMs were 2.4 to 63.5 KB, so the 4 MB cap is not a concern, and the plain fetch of fimportal pages is already 70 KB of server-rendered HTML. `/snapshot`, `/screenshot`, JPEG against PNG sizes and the daily-limit `429` body were not probed (the rate-limit `429` stopped the run); chapter 19 must probe them before it depends on them. |
| D27 | **The screenshot probe settled the capture contract (chapter 19, 2026-10-27).** `/screenshot` answers with **raw image bytes** (`image/jpeg` or `image/png`, no envelope, no DOM), while `/snapshot` with `formats: ["content", "screenshot"]` answers with the JSON envelope `{success, result{content, screenshot (base64)}, meta{status, title, headers, finalUrl}}` and the screenshot inside it is byte-identical to the one `/screenshot` returns for the same options (63,443 B for `example.com`). `/snapshot` cost 1,179 ms against 1,262 ms for `/screenshot` on `example.com`, so there is no cost reason to leave `/snapshot`: it also yields the DOM (the password-field login guard works) and the target's `meta.status` and `meta.finalUrl`, so the capture handler refuses an error status and records the final URL exactly as `render_page` does. JPEG quality 80 full page was 63,443 B (`example.com`) and 299,161 B (the fimportal SPA page); PNG of `example.com` was 75,533 B and took 4,232 ms (JPEG 1,262 ms), so JPEG stays. `X-Browser-Ms-Used` was a readable integer on all four screenshot calls (1,262, 4,232, 1,179 and 2,235 ms). No `429` occurred; the daily-limit body is still unprobed. The capture task's `target_url` is the extract task's `target_url` (the artifact's `source_url`, already the redirect-resolved URL of the plain fetch), because `PageContext.final_url` is always `None` in the extract handler. Browser seconds spent on the probe: about 8.9 s of header-reported time over four calls. |

## Open seams

| Seam | Placeholder | Forcing condition |
| --- | --- | --- |
| Resolve mentions to canonical documents and emit `new_requirement` suggestions | Mentions are staged with roles; no emit | Enough documents promoted to reference |
| Web voting and moderation UI | API votes and promotion exist; the web screens are [voting-moderation](../voting-moderation/01-rollout.md) chapters 10–11 | Operators need to approve candidates without API calls |
| Attach artifacts to suggestions as `evidence` rows | Artifacts stay linked to staging only | [evidence-storage](../evidence-storage/00-architecture.md) model and routes ship |
| Re-extraction on extractor version bump | `input_key` makes it possible; no admin trigger | First extractor revision |
| Link-following frontier and crawl budgets | Not built; sources are catalogue `portal_url`s | Someone wants discovery of unseen pages |
| Freshness crawling | Not built | Product treats stale documents as a visible problem |
| LLM extraction | Planned as its own suite, [extraction](../extraction/00-architecture.md); consumes the snapshots of chapter 15. Hand-written extractors (chapter 18) become optional | The extraction suite starts after chapters 14, 15 and 23 |
| Cloudflare Workflows (and bindings) as a consumer of the machine API | Not built. Cloudflare Queues were rejected: the free plan keeps messages 24 hours, far less than the backlog lives. Workflows are attractive (durable steps, sleep until the quota resets, no tokens or Actions minutes) but the free plan gives 10 ms of CPU per step and 3,000 steps a day, and it would duplicate the Python worker in TypeScript | Actions minutes, not Cloudflare limits, bottleneck the render and LLM drains, and a spike shows a 10 ms step is enough |
| Snapshot and screenshot retention beyond "latest two" | None for screenshots | Stored bytes approach `OBJECT_STORE_MAX_BYTES` |
| Plain-first rendering: keep the plain body as the snapshot for pages that are already server-rendered and call Cloudflare only for thin shells | Every successful HTML page is rendered, so one snapshot shape feeds every extractor | The free allowance makes the render backlog too slow, or the probe shows most pages are static. The chapter 15 probe found the plain fetch of fimportal pages is already 70 KB of server-rendered HTML (the rendered DOM is 62 to 64 KB): diff the two before the 22-run backlog starts |
| Viewport-only screenshot retry for pages whose full-page JPEG exceeds 8 MB | Such pages complete with `oversize` and no image | Oversize notes appear on pages that matter |
| Paid Cloudflare plan | Not needed; lower `BROWSER_MIN_INTERVAL_SECONDS` to use it | The free throttle becomes the bottleneck for freshness work |
| A `metadata` claim from steckbrief text (the label is fixed; the real steckbrief has no `kurztext`, D25) | Entities get a label and the `new_document` claim but no `metadata` claim | Someone wants steckbrief text such as `leistungsbezeichnung_2` as a claim; that needs a decision on the claim shape |
| Stammtext fetch from steckbrief `leistung_stammtexte` references to find Unterlagen or forms | Not probed; the steckbrief itself has no document fields (D25) | The document-first path needs more mention sources than PVOG payload and page extraction |
| Rename `apps/discovery-ingest` | Keep the name | The package no longer fits its name |

## Risks

| Risk | Mitigation |
| --- | --- |
| Postgres enum labels cannot be removed on downgrade | Add all three labels in one migration; document the downgrade as label-preserving; rely on the kind filter for safety |
| boto3 default checksum headers may be rejected by R2's S3 layer (a known trouble with non-AWS stores) | Adapter starts with `when_required`; the live probe workflow decides the client checksum configuration before any upload code depends on it |
| R2 bills past 10 GB, 1M Class A and 10M Class B operations a month | App-level cap and operation counters (D24); Coverage shows bytes against the cap; screenshots only for pages with mentions; snapshots limited to the latest two per service at 4 MB; the operator sets a Cloudflare billing notification |
| An artifact object can be orphaned (chapter 14): pruning deletes rows first and objects best-effort, an upload whose row insert fails after `put` leaves an unreferenced object, and two concurrent identical uploads race on the unique key (one answers 500) | Accepted. The byte cap sums database rows, so orphans are not counted; the 2 GiB margin below R2's 10 GB absorbs them, and a re-upload of the same bytes overwrites the object. The drain runs one upload at a time. A reconciliation sweep (needs `list`, a Class A call) stays an open seam |
| Workers AI bills if the account is moved to Workers Paid | Neuron cap and reservation in the ledger (D23); the operator keeps the Workers Free plan (chapter 22) |
| The Supabase database goes read-only at 500 MB | 400 MB soft limit on machine writes (D24); bodies and bytes never go to Postgres (D9) |
| The shared GitHub Actions quota (2,000 minutes across repositories) runs out and every repository's jobs fail | This repository capped at 1,000 minutes a month with a CI reserve; drain workflows report minutes to the ledger and skip themselves; schedules off by default; local runs for the backlog (D24) |
| `fimportal.de/detail/L/...` pages may be JavaScript-rendered | Rendered by Cloudflare (D14), so the snapshot holds the DOM; chapter 15's probe compares a shell page's plain and rendered sizes. FIM API enrichment (chapter 12) and payload harvest remain the primary sources |
| The free Cloudflare allowance makes the render backlog slow | About 4 pages a minute and roughly 22 fifteen-minute runs for the known 1,423 pages; local runs cost no Actions minutes; pages are rendered in queue order, so partial progress is useful; plain-first (open seam) and the paid plan are the escape hatches |
| The quick action does not document its error or quota behaviour in detail | Chapter 15 starts with a probe that records response shape, `X-Browser-Ms-Used`, error cases and a `429` body; every limit is handled by release, so a surprise stops a run instead of failing tasks |
| Sites or WAFs may block Cloudflare's signed, automated traffic | Render failures are per page and retried with backoff; no bypass is attempted (invariant 8); the plain fetch result and PVOG payload harvest still exist |
| The Cloudflare token is a new credential in GitHub Actions | Scoped to Browser Run - Edit only, never in Render or the web app (invariant 11); rotate by replacing the secrets and running the probe |
| Page content is sent to a third-party browser service | Only public catalogue URLs are rendered; login walls are skipped |
| robots.txt and terms across 123 hosts | Respect robots.txt, identify the bot, rate limit per host, no login-wall bypass, skip on denial |
| Candidate names harvested from free text are noisy | Staged, deduplicated and reviewed before any emit; excerpts and source fields shown to the reviewer |
| The `.plans/README.md` status lines for voting-moderation lag the code | Noted in chapter 21; correcting another suite's status is left to its owner |
